# Резерв при медленной сети

Текущий CPU DINO proposal baseline измерен и непригоден по качеству; не использовать его как готовый detector. Qwen/CUDA сейчас дозагружаются, их процессы не дублировать. Partial сохраняется и проверяется официальным SHA256 перед установкой.

Подготовлен технический резерв: официальный Qwen3-VL-2B-Instruct-GGUF, text Q4_K_M + соответствующий F16 mmproj, portable llama.cpp Windows. Код runtime MIT, веса Apache-2.0. Источники и точные имена — config/fallback-gguf.json. Такой путь убирает зависимость от полного PyTorch CUDA wheel; это ещё не измеренное ускорение и не доказательство качества quantization.

Порядок: сначала проверить, завершены ли текущие загрузки; продолжить partial при рабочем прогрессе. Если CUDA остаётся сетевым blocker, подготовить отдельный portable runtime и закрепить release/hash/лицензии, скачать только выбранную пару GGUF, проверить SHA256. Не использовать глобальную переустановку, winget, Docker, service install или изменение защиты ОС. После чтения фактического --help — только loopback backend, offline local paths, затем реальный TRAIN benchmark на последовательностях кадров. Выбрать бюджет по измеренным latency/RAM/VRAM, сравнить на том же tuning split, holdout оставить закрытым. Нельзя считать этот резерв рабочим до запуска и валидации.

Новые GGUF/runtime загрузки и listeners пока не запускались: основной поток продолжает текущие артефакты. API-ключ и внешний HTTPS relay этим резервом не создаются.
