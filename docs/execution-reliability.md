# Historical diagnosis and bounded reporting

The initial HYBRID-R22-01 attempt has a fixed-schema failure report: native readiness timed out at the frozen `NativeServer.start` deadline. A separate artificial loopback check returned Windows10013 inside the execution network sandbox and passed outside it. No OS network/security settings were changed. This supports the initial startup diagnosis; it does not establish the later recovery's termination cause.

The recovery left only a running marker and a safe progress snapshot:16 completed fictional text controls,10 passed. No final visual-control or TRAIN aggregate exists. Later technical inspection confirmed both the recorded native PID and the exact recovery-runner process were absent. Their actual exit code was never persisted and cannot be reconstructed after the handles/processes disappeared. The exit1/FileExistsError from the rejected invocation belongs to the duplicate-attempt guard, not the original model worker. Empty native log sizes establish no semantic or crash cause; raw logs/answers were not read. No OOM, driver, transport or model-quality cause is asserted.

Source gaps explain why a terminal report could be missing: the worker itself owned final publication, `except Exception` cannot handle forced process termination, and there was no independent parent recording the actual return code. A per-phase HTTP timeout is also not an external absolute process watchdog. These are reliability gaps, not proof of a specific historical kill mechanism.

`cashreview/supervision.py` provides a prospective monitor for cooperative workers. It uses a fresh run directory, an exclusive owner identity, a start gate and a Windows kill-on-close Job Object. The worker waits before spawning descendants. The monitor owns the actual process handle, enforces a monotonic deadline, records exit code and cleanup, validates only fixed-schema safe summaries, preserves aggregate progress and publishes an atomic/fsynced terminal result. Contradictory completed/server-failed reports cannot pass. Status persistence precedes the authoritative terminal; late commits are revoked before fallback writes. Forced monitor exit closes its job handle; later reconciliation records interruption with unknown exit code instead of inventing a cause.

The [Windows Job Object API](https://learn.microsoft.com/en-us/windows/win32/api/jobapi2/nf-jobapi2-assignprocesstojobobject) scopes these limits to the owned process tree; no firewall, security policy, credentials or persistent grants are changed. Kill-on-close uses the documented [extended job limits](https://learn.microsoft.com/en-us/windows/win32/api/winnt/ns-winnt-jobobject_extended_limit_information).

Synthetic tests cover success, failed controls, exception, hard exit7, fake server exit9, deadline, missing/invalid report, stale gate/report rejection, worker orphan cleanup, monitor hard kill/reconciliation, primary/final-status write errors, slow persistence and post-replace timeout plus failed fallback. They load no models/media and perform no inference. Test counts/timing are regenerated from JUnit into safe aggregates and the claim ledger.

The final integration suite also exposed a PID-file publication race: an orphan-test reader observed the file between creation and content write. Workers now flush/fsync a same-directory temporary PID file and rename it atomically before model imports. This is a separate observed implementation defect; it does not establish the old hybrid recovery's unknown termination cause. Both the failed suite result and the post-fix result are retained privately.

Limits: a dead monitor cannot retrospectively recover an unrecorded child exit code. Storage unavailable for every write or invalidation remains an operational failure; do not treat a missing/incomplete report as success. The new monitor is not retroactively applied to the frozen failed hybrid, and it does not authorize another semantic-gate run.
